# Ticket 03: Connect the Static Election Data

## Goal

Load the existing election JSON files into the new application as static frontend data while preserving the current data structures.

## Context

The rebuild has no backend. Election data must be available to the frontend at build or runtime as static files. Some files may currently exist only locally or may be generated by the existing scripts, so their source and required location must be clarified before implementation is complete.

## Scope

- Identify every JSON file required for the one-page experience.
- Confirm the expected file names and the model used by each file.
- Decide on a single static location inside the new application.
- Copy or generate the required files into that location once they are available.
- Add small data-loading modules that return strongly typed data.
- Normalize only differences that already exist between raw property names and application models, such as `districts_won` to `districtsWon`.
- Show a clear English error state if required data cannot be loaded.
- Document where the files come from and how they are placed or generated.

## Implementation details

Review the currently referenced data, including:

- second-vote entries,
- statistical vote entries,
- party metadata,
- direct-mandate results,
- Germany map data if it remains part of the filter interface.

The data loader should be the only part of the new application that knows the concrete file locations. React presentation components should receive typed data and should not contain raw JSON transformation code.

Do not introduce network APIs. Static imports or frontend fetches from the application assets are sufficient.

## Acceptance criteria

- All data required by the one-page scope is listed and documented.
- Every required file has a defined location in the new application.
- The application loads party data, vote data, and direct-mandate data without importing from the legacy application folder.
- Loaded values conform to the preserved TypeScript contracts.
- Necessary property mapping is contained in data-loading code rather than UI components.
- Missing or invalidly shaped top-level data produces a visible English error message instead of a blank page or unhandled exception.
- No backend, server endpoint, or external database is required.
- The application build succeeds when the documented static files are present.

## Out of scope

- Changing the JSON schema.
- Rebuilding the Python or notebook data pipeline beyond what is needed to recover the files.
- Downloading live data from official sources at application runtime.
- Supporting multiple election years.
- Adding a general data-access framework.

## Dependencies

- Ticket 01: Bootstrap the new one-page application.
- Ticket 02: Preserve the existing JSON contracts.
